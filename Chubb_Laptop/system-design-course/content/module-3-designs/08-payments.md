# Design 08: Payment & Wallet System

> **Lesson 3.8** · Senior · 90 min

## Problem Statement

Design a digital wallet and payment system where:
- Users can add money (top-up) from a bank/card
- Users can transfer money to other users (P2P)
- Users can pay merchants
- Full transaction history
- Never lose money (exactly-once processing, no double-charges)

---

## Step 1: Clarify Requirements

**Functional:**
1. Add funds (link bank account or card)
2. P2P transfer (send money to another user)
3. Pay a merchant
4. View transaction history
5. Refunds

**Non-functional:**
- 200M active wallets
- 1M transactions/day
- Money must NEVER be lost or double-spent
- Transactions must be idempotent (retry-safe)
- Audit trail: every state change logged forever
- PCI-DSS compliance (no storing raw card numbers)
- 99.999% availability (5 nines — payment downtime = lost revenue)

---

## Step 2: The Fundamental Rule — Double-Entry Bookkeeping

Invented by merchants in 15th century Italy. Every transaction creates two entries that sum to zero. Money is never created or destroyed, only moved.

```
Alice sends Bob $50:

Entry 1: Alice's account  DEBIT  $50   (balance decreases)
Entry 2: Bob's account    CREDIT $50   (balance increases)

Sum of all entries = $0  ✓  (money conserved)
```

**This is how banks actually work.** Your "bank balance" is just the sum of all credit and debit entries for your account.

**Advantage:** If the system crashes mid-transfer, you can detect inconsistency: sum of all entries must always be $0. Any other result = data corruption.

## Step 3: Database Schema

```sql
-- Accounts (wallets)
CREATE TABLE accounts (
    id          BIGSERIAL PRIMARY KEY,
    user_id     BIGINT UNIQUE NOT NULL,
    currency    CHAR(3) NOT NULL DEFAULT 'USD',
    balance     DECIMAL(18,2) NOT NULL DEFAULT 0.00,
    created_at  TIMESTAMP DEFAULT NOW(),
    CONSTRAINT balance_non_negative CHECK (balance >= 0)
);

-- Transactions (ledger entries)
CREATE TABLE transactions (
    id              BIGSERIAL PRIMARY KEY,
    idempotency_key UUID UNIQUE NOT NULL,   -- prevent duplicates
    type            VARCHAR(20),            -- topup, transfer, payment, refund
    status          VARCHAR(20),            -- pending, completed, failed, reversed
    amount          DECIMAL(18,2) NOT NULL,
    currency        CHAR(3) NOT NULL,
    description     TEXT,
    created_at      TIMESTAMP DEFAULT NOW(),
    completed_at    TIMESTAMP
);

-- Ledger entries (double-entry accounting)
CREATE TABLE ledger_entries (
    id              BIGSERIAL PRIMARY KEY,
    transaction_id  BIGINT NOT NULL REFERENCES transactions(id),
    account_id      BIGINT NOT NULL REFERENCES accounts(id),
    entry_type      CHAR(6) NOT NULL,   -- DEBIT or CREDIT
    amount          DECIMAL(18,2) NOT NULL,
    running_balance DECIMAL(18,2) NOT NULL,  -- balance AFTER this entry
    created_at      TIMESTAMP DEFAULT NOW()
);
```

Account balance can be computed two ways:
1. `SELECT balance FROM accounts WHERE id = X` — fast, denormalized
2. `SELECT SUM(CASE WHEN entry_type='CREDIT' THEN amount ELSE -amount END) FROM ledger_entries WHERE account_id = X` — slow but authoritative

Both should agree. Periodic reconciliation verifies consistency.

## Step 4: The Transfer Flow (with ACID)

```sql
BEGIN TRANSACTION;

-- Step 1: Idempotency check
SELECT id FROM transactions WHERE idempotency_key = 'uuid-xxxx';
-- If row exists → return existing transaction (do NOT re-execute)

-- Step 2: Check sender balance
SELECT balance FROM accounts WHERE id = sender_id FOR UPDATE;
-- FOR UPDATE locks the row — prevents concurrent transfers from this account
IF balance < amount THEN ROLLBACK; RAISE 'insufficient funds';

-- Step 3: Create transaction record
INSERT INTO transactions (idempotency_key, type, status, amount, ...)
VALUES ('uuid-xxxx', 'transfer', 'pending', 50.00, ...);

-- Step 4: Debit sender
UPDATE accounts SET balance = balance - 50.00 WHERE id = sender_id;
INSERT INTO ledger_entries (transaction_id, account_id, entry_type, amount, running_balance)
VALUES (txn_id, sender_id, 'DEBIT', 50.00, new_sender_balance);

-- Step 5: Credit recipient
UPDATE accounts SET balance = balance + 50.00 WHERE id = recipient_id;
INSERT INTO ledger_entries (transaction_id, account_id, entry_type, amount, running_balance)
VALUES (txn_id, recipient_id, 'CREDIT', 50.00, new_recipient_balance);

-- Step 6: Complete
UPDATE transactions SET status = 'completed', completed_at = NOW() WHERE id = txn_id;

COMMIT;
```

Either ALL of these steps succeed or NONE of them do (ACID atomicity). No partial states.

## Step 5: Idempotency — The Most Important Pattern

Network calls fail. The client retries. Without idempotency, the retry creates a second transaction.

**Idempotency key:** A UUID generated by the client, sent with every transaction request. The server stores it and checks it before processing:

```python
def transfer(idempotency_key, sender_id, recipient_id, amount):
    # Check if already processed
    existing = db.query("SELECT * FROM transactions WHERE idempotency_key = ?", key)
    if existing:
        return existing  # return the SAME result as before
    
    # Process new transaction
    ...
```

Client behavior:
1. Generate idempotency key (UUID) before making the request
2. If network times out → retry with the SAME key
3. If already processed → server returns same result → client happy

**The idempotency key must be unique per logical transaction attempt, not per retry.** The client generates one UUID per "I want to send $50 to Bob" event.

## Step 6: Handling External Payment Providers

Users top up wallets via card/bank. This involves Stripe/Braintree/ACH.

```
User charges card for $100 topup
         │
         ▼
Payment Service → Stripe API (charge card)
         │
         ▼ Success
Create transaction (type=topup, status=pending)
         │
         ▼
Stripe webhook: payment_intent.succeeded
         │
         ▼
Update transaction status = completed
Credit user wallet +$100
```

**Why webhook?**

The initial API call confirms the charge was initiated. The webhook confirms it actually cleared. Credit cards can be declined after initial authorization (fraud detection triggers late, bank goes offline).

Never credit the wallet until the webhook confirms success. Handle the time between initial response and webhook with a "pending" state.

## Step 7: Dealing with Failures

**What if the database crashes mid-transfer?**

ACID guarantees rollback. The transaction is either fully committed or fully rolled back. Check `transactions.status` — if it is still "pending" after 5 minutes, the transaction failed to complete. Run compensation logic.

**What if the external payment succeeds but our DB crashes before we credit the wallet?**

This is the hardest case. The user was charged but the wallet was not credited.

**Solution:** Outbox pattern + idempotent webhook processing.
1. When initiating topup, write to an `outbox` table in the same DB transaction
2. A separate process reads the outbox and processes webhooks
3. Webhook processing is idempotent (uses Stripe's `payment_intent` ID as idempotency key)

---

## Step 8: Compliance and Security

**PCI-DSS:** Never store raw card numbers. Use Stripe's tokenization — your system stores only a token (`tok_xxxx`) that references the card in Stripe's secure vault.

**Audit log:** Every state change is immutable. Ledger entries are never updated or deleted. This is the legal record.

**Fraud detection:**
- Velocity checks: > 5 transfers in 1 hour → flag for review
- Unusual amounts or recipients → ML model scores transaction
- Risky transactions: hold for 24-hour manual review
